# Pulse security (Roadmap 5.3)

## Threat model

Pulse is a read-mostly public intelligence API. The assets are the
ingested document store, the API keys, and the trust of the people who
read its answers. The threats it defends against, in order:

1. **Abuse of the query API** — a caller hammering the endpoint or
   exhausting a quota. Mitigated by per-key rate limits, per-consumer
   daily quotas, and usage/audit records that make abuse visible.
2. **SSRF through ingestion** — a feed URL (or redirect) pointing at
   internal services. Mitigated by the SSRF guard (see below).
3. **Credential exposure** — API keys or DB passwords leaking into
   logs, files, or git. Mitigated by key fingerprints (never the key),
   masked config output, and the no-secrets-in-files rule.
4. **Fake data** — invented articles, statistics or citations entering
   the store and being served as real. Mitigated by provenance on
   every record and the "no answer is better than a wrong answer" rule.
5. **Unauthorized Facebook access** — the connector touching Facebook
   without a Meta app or authorized Page. Mitigated by running
   unconfigured until the operator creates the app and the partnerships.
6. **Availability** — a single host going down. Mitigated by backups
   (`pulse backup` / `pulse restore`) and the runbook in
   `docs/OPERATIONS.md`. There is no multi-region deployment (see
   `docs/SCALABILITY.md` for the extension points).

Pulse does **not** defend against a compromised host, a leaked
database password, or a malicious operator — those are deployment
concerns, handled by the reverse proxy, the database's own auth, and
access control on the host.

## SSRF protection

Every ingestion fetch target is range-checked **before** connect
(`src/ingestion/ssrf.zig`): loopback, private, link-local, CGNAT,
documentation, benchmarking, multicast and reserved ranges are
refused, for both IPv4 and IPv6 (including IPv4-mapped IPv6). A
hostname is resolved and **every** returned address must be public.
Redirects are checked hop by hop.

Known residual gap: the check and the connect are two steps, so a DNS
record that flips between them is not fully closed. Operator-configured
POST provider endpoints are **not** checked — a local Ollama instance
is a legitimate target.

## API keys and rotation

- Keys are random 32-byte hex, generated by `pulse keygen`.
- `PULSE_API_KEY` is the current key. `PULSE_API_KEY_PREVIOUS` is the
  old key, accepted alongside the current one during rotation.
- Rotation procedure:
  1. Generate a new key: `./zig-out/bin/pulse keygen`.
  2. Put the new key in `PULSE_API_KEY`, the old key in
     `PULSE_API_KEY_PREVIOUS`. Restart Pulse.
  3. Migrate clients to the new key (each key has its own rate-limit
     bucket, so rotation never shares a budget).
  4. Remove `PULSE_API_KEY_PREVIOUS` and restart.
- `pulse audit` fails when both keys are identical (rotation never
  happened) and warns when only the previous key is set.
- Keys are compared in constant time. The audit log stores only the
  first 8 hex chars of SHA-256(key) — the key itself never appears in
  any log, file, or database row.

## Audit records

Every authenticated `/v1/query` call
writes one record — including denials (bad key, unknown consumer,
missing scope, rate limit, quota). A record holds: UTC timestamp,
consumer, key fingerprint, route, method, HTTP status, request id.
No user content, no key.

Sinks (best-effort, never fail a request):

- Postgres `audit_log` table (migration 011) when `DATABASE_URL` is set.
- JSONL file when `PULSE_AUDIT_LOG` is set (one record per line).
- Structured log line, always.

Read them with SQL (`SELECT * FROM audit_log ORDER BY ts DESC LIMIT
100`) or by reading the JSONL file. There is no API to read audit
records back — the log is append-only by design.

## Pre-flight audit

Run `./zig-out/bin/pulse audit` before any production deployment. It
checks: API key configured, rotation sanity, rate limits sane,
retention enabled, TLS termination flagged (`PULSE_BEHIND_TLS_PROXY`),
linked dependencies (Zig version, libzstd), live Postgres version +
required extensions (`vector`, `postgis`, `pg_trgm`), live Redis
maxmemory + eviction policy. Any FAIL exits 1.

## TLS

Pulse serves plain HTTP. **The Zig 0.17.1 stdlib has no TLS server**
(verified: no `Server` in `lib/std/crypto/tls.zig`), so TLS
termination is the reverse proxy's job — never Pulse's. In production
run behind a TLS-terminating proxy and set `PULSE_BEHIND_TLS_PROXY=1`
so `pulse audit` knows termination is in place. `pulse audit` warns
while the flag is unset.

For outbound fetches, `PULSE_REQUIRE_HTTPS_FETCHES=1` refuses
plain-http feed URLs (default 0 — one registry feed, Daily Observer,
is http-only).

## Dependency auditing

`pulse audit` reports the linked Zig version and libzstd version and
fails when libzstd is older than 1.5.0. There are no other runtime
dependencies for the API itself: the server is a single static Zig
binary plus Postgres, Redis and (optionally) MinIO — and, in the
all-in-one image, the bundled SearXNG (granian + a Python venv with
the pinned SearXNG source; see `docs/WEBSEARCH.md`). Upgrade Zig by
rebuilding; upgrade libzstd on the host and re-run `pulse audit`.

## Input validation

- Query: 1–1000 chars, non-empty after trimming; `options.limit` 1–20.
- Ingest: title ≤500 chars, text ≤20000 chars, URL must be http(s),
  `source_id` must name a registered source; documents fail
  `validate.validate` (title/URL/text/source) before storage.
- Consumer names: 1–64 chars of `[a-z0-9_-]`.
- Feed URLs: SSRF-checked (above) and, in strict mode, https-only.

## What is NOT built

- No WAF, no IP allowlisting, no per-IP rate limiting (limits are
  per API key). Add those at the reverse proxy.
- No user accounts or passwords inside Pulse — the only credential is
  the API key.
- No encryption at rest beyond what Postgres/Redis/MinIO provide.
- No secrets rotation for the database password — rotate it in the
  deployment, then update `DATABASE_URL` and restart.
